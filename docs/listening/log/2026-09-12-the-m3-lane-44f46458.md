## Did the tools help? — the honest answer this thread owes

- ✅ **Recording worked, and it works on ANY song URL.** That is wider than `suno.mts record`,
  which can only reach takes visible in the create page's list. Navigating to the song page and
  clicking its Play button is what the 2026-09-11 experiment did in the first place; the shipped
  command narrowed it.
- ✅ **Measurement was cheap and told us something.** Loudness range answered "have we got
  dynamics" in one number, and the tempo reading raised a question nobody had asked.
- ❌ **Describing did not happen.** The half that would name genre, instruments and vocal character
  is the blocked half (listen-mcp T3 — AI Studio refuses Chrome for Testing). So measurements are
  a floor here, not a substitute.
- 🔑 **And for "what style is this?", neither half was needed.** The answer was written on the page.

## Two mechanical notes for whoever builds `record-url`

- **Stop detection failed.** The poll waited for the audio element's `currentTime` to reach its
  `duration` and it never did, so the capture ran to a 6-minute deadline and caught 6:19 for a
  3:35.8 song — Suno auto-advanced into the next track. Trimming to the player's reported
  `duration` (215.761 s) from the first sound recovered it exactly, but the loop needs a better
  end signal than `currentTime`.
- **WSLg's audio server was hung** (`pactl info` times out; the socket at `/mnt/wslg/PulseServer`
  exists but does not answer), which would normally make recording impossible. Worked around by
  running a **private PulseAudio inside WSL** with its own runtime path and null sinks, and
  pointing the browser at it with `PULSE_SERVER`. Live audibility is lost that way — there is no
  loopback to Windows — but capture is unaffected, and WSLg was silent anyway. This avoided a
  `wsl --shutdown`, which would have killed all nine sessions.
